# Note Taking

Capture the idea that will still be useful later, not the chronology of how the conversation happened.

## Start with the durable point

Before drafting, identify:

1. the question or problem the note answers;
2. the main conclusion or insight worth preserving;
3. the evidence, examples, caveats, or source material needed to trust and reuse it.

If there is no stable takeaway yet, keep the note exploratory and say what remains unresolved rather than manufacturing a conclusion.

## Write for future reuse

Prefer a self-contained note over a transcript. A future reader should be able to understand the important idea without reconstructing the conversation that produced it.

Preserve details when they materially affect the conclusion: exact snippets, commands, equations, measurements, constraints, references, failed approaches that explain a decision, and uncertainty that changes how the result should be used. Remove conversational repetition, dead ends that add no evidence, and routine setup that can be reconstructed easily.

Use the shortest structure that makes the note easy to recover later. A good default is:

**Context or problem → key idea → explanation or evidence → caveats → supporting detail.**

Do not add sections merely to make the note look formal.

## Keep claims grounded

Distinguish among facts from sources, observations from a particular environment, user-supplied assumptions, and conclusions inferred from them. Keep important uncertainty visible. Do not turn a one-off observation into a universal rule without evidence.

## Route specialized work

When code, a technique, or implementation guidance is central, apply the `technical-writing` skill so the distinctive mechanism is easy to find and routine glue does not dominate the note.

When the user asks to save, publish, merge, or verify a note in `luckyrandom/chat-notebook`, apply the `chat-notebook-publisher` skill. Drafting a note does not by itself authorize repository changes or publication.
